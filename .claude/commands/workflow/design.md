# Design Command

> Create architecture and technical specification in one pass (Phase 2)

## Usage

```bash
/design <define-file>
```

## Examples

```bash
/design .claude/sdd/features/DEFINE_CHECKOUT_API.md
/design DEFINE_USER_AUTH.md
/design .claude/sdd/features/DEFINE_INVOICE_EXTRACTION.md
```

---

## Overview

This is **Phase 2** of the 5-phase AgentSpec workflow:

```text
Phase 0: /brainstorm → .claude/sdd/features/BRAINSTORM_{FEATURE}.md (optional)
Phase 1: /define     → .claude/sdd/features/DEFINE_{FEATURE}.md
UX Gate: /ux-review  → .claude/sdd/reviews/UX_REVIEW_{FEATURE}.md
Phase 2: /design     → .claude/sdd/features/DESIGN_{FEATURE}.md (THIS COMMAND)
Phase 3: /build      → Code + .claude/sdd/reports/BUILD_REPORT_{FEATURE}.md
Phase 4: /release    → production + ledger .claude/sdd/releases/
```

The `/design` command combines what used to be Plan + Spec + ADRs into a single document with architecture decisions inline.

---

## What This Command Does

1. **Analyze** - Understand requirements from DEFINE and UX_REVIEW when present
2. **Architect** - Design high-level solution with diagrams
3. **Decide** - Document key decisions with rationale (inline ADRs)
4. **Specify** - Create file manifest and code patterns
5. **Plan Testing** - Define testing strategy

---

## Process

### Step 1: Load Context

```markdown
Read(.claude/sdd/features/DEFINE_{FEATURE}.md)
Read(.claude/sdd/reviews/UX_REVIEW_{FEATURE}.md)  # if present
Read(.claude/sdd/templates/DESIGN_TEMPLATE.md)
Read(.claude/CLAUDE.md)

# Explore codebase for patterns:
Glob(**/*.py) | head -20
Grep("class |def ") | sample
```

**Extract the `LLM Prompts` flag** from the Technical Context section of the DEFINE. Canonical values: `true` or `false`. If the line is missing or blank → treat it as **ambiguous** and fire `AskUserQuestion` before proceeding (a sign the DEFINE was generated by an older version of the template; ask for `/iterate DEFINE` if the user cannot answer).

**Defensive re-check** (silent): even with `LLM Prompts: false`, run the `/define` Step 5.5 heuristic against the material extracted from the DEFINE + UX_REVIEW + the design scope drafted so far. If hits > 0 while the flag says `false`:

> "The DEFINE says `LLM Prompts: false` but I detected signals: `<list>`. (a) `/iterate DEFINE` to fix it, (b) confirm these are false positives and continue with `false`, (c) flip the flag to `true` in this DESIGN (the DESIGN then diverges from the DEFINE — record it in Revision History)?"

### Step 2: Create Architecture

Design the solution:

| Component | Content |
|-----------|---------|
| **Overview** | ASCII diagram of system |
| **Components** | List of modules/services |
| **Data Flow** | How data moves through system |
| **Integration Points** | External dependencies |

### Step 3: Document Decisions (Inline ADRs)

For each significant choice:

```markdown
### Decision: {Name}

| Attribute | Value |
|-----------|-------|
| **Status** | Accepted |
| **Date** | YYYY-MM-DD |

**Context:** Why this decision was needed

**Choice:** What we're doing

**Rationale:** Why this approach

**Alternatives Rejected:**
1. Option A - rejected because X
2. Option B - rejected because Y

**Consequences:**
- Trade-off we accept
- Benefit we gain
```

### Step 4: Create File Manifest

List all files to create/modify:

| # | File | Action | Purpose | Dependencies |
|---|------|--------|---------|--------------|
| 1 | `path/to/file.py` | Create | Main handler | None |
| 2 | `path/to/config.yaml` | Create | Configuration | None |
| 3 | `path/to/handler.py` | Create | Request handler | 1, 2 |

### Step 5: Define Code Patterns

Provide copy-paste ready code snippets for key patterns.

### Step 5.5: LLM Prompts — attach fragment (conditional)

**If `LLM Prompts: false`** in the DEFINE (and the re-check confirmed it) → **skip** this step. Attach nothing. Do not invoke your prompt-engineering skill.

**If `LLM Prompts: true`:**

1. Add an **"LLM Prompts"** section to the generated DESIGN, between **"Code Patterns"** and
   **"Data Flow"**: an **Inventory table** (one row per planned runtime prompt: path · `Type`
   · consumer · output shape) followed by a **"Per-prompt contract"** block per row.
2. (The section is authored inline — there is no fragment to attach.)
3. Fill the **Inventory** with one row per planned runtime prompt (cross-check against the File Manifest — every file matching the glob `**/prompts/**`, or any service that calls an LLM API, must have a row). **Classify the `Type` column of each row** using the builder router: `one-shot` (single call → your prompt-engineering skill, configured in `sdd.config.yaml`) vs `loop` (an iterative LLM process reason→act→observe→adjust → your loop-specification skill first, then the prompt-engineering skill per stage). Decisive signal: *does the process re-prompt the LLM based on its own previous output?* Yes → `loop`. When in doubt, `AskUserQuestion`.
4. For **each inventory row**, fill the "Per-prompt contract" block with:
   - Tone/audience extracted from the DEFINE/UX_REVIEW (do not invent it).
   - Output type derived from the consumer's schema (downstream service / DB column / template render).
   - Approved fallback, citing the DEFINE section it comes from.
   - Reference material as concrete refs (`[file:line]`) or a raw copy of the schema/policy.
   - Decisions already settled (provider, model, version) — closing them here avoids reopening them in `/build`.

**Do not invoke your prompt-engineering skill (or the loop-specification skill) in this step.** Invocation happens in `/build` Step 4 (routed by the `Type` column), with the compiled contract in hand. The DESIGN only records the classified inventory + contract.

### Step 6: Plan Testing Strategy

| Test Type | Scope | Tools |
|-----------|-------|-------|
| Unit | Functions | pytest |
| Integration | API | pytest + requests |
| E2E | Full flow | Manual/automated |

### Step 7: Save

```markdown
Write(.claude/sdd/features/DESIGN_{FEATURE_NAME}.md)
```

## 🤝 (Optional) Second-opinion review — challenge the approach BEFORE coding

> **A recommendation; the call is the user's.** This is the point of **highest ROI** for a second
> opinion: the cost of changing the approach is low here and very high after `/build`. A
> second-opinion review from a different model vendor, independent of the primary model, questions
> the DESIGN's assumptions and trade-offs — not comma-level defects.

Before `/build`, from the **feature worktree**, consider requesting a second-opinion review of
`.claude/sdd/features/DESIGN_{FEATURE_NAME}.md` from a different model vendor.

- Only **you** trigger it; the agent merely suggests it when it makes sense.
- Skip it for trivial changes (1–2 files) — a redundant review only dilutes the signal.
- **Contract for the request and the response:** compile the request and require the format in
  [`fragments/ADVISOR_CONSULT.md`](../../sdd/templates/fragments/ADVISOR_CONSULT.md)
  (VERDICT · TOP RISKS ≤3 · SPECIFIC FIXES · WHAT TO IGNORE, ≤300 words). Every note received is
  **APPLIED or REBUTTED** in the DESIGN changelog (Advisor Ledger) — ⛔ never discarded silently.

## Quality Gate

Before saving, verify:

```text
[ ] Architecture diagram is clear
[ ] All major decisions documented with rationale
[ ] File manifest is complete (all files listed)
[ ] Code patterns are copy-paste ready
[ ] Testing strategy covers requirements
[ ] No circular dependencies in architecture
[ ] If LLM Prompts=true: fragment attached, inventory covers 100% of the manifest files under **/prompts/**, contract filled for every row
[ ] If LLM Prompts=false: defensive re-check run and zero hits confirmed (or the divergence recorded in Revision History)
```

---

## Tips

1. **Diagram First** - ASCII art clarifies thinking
2. **Decisions Are Permanent** - Document the "why" not just "what"
3. **Self-Contained Files** - Each file should work independently
4. **Config Over Code** - Use YAML for tunables, not hardcoded values
5. **Test Early** - Design for testability from the start
